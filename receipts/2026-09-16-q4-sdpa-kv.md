## What was tried

All arms change only the f16 arm of
`overlay/mlx/backend/omarchy/shaders/sdpa_decode_native.comp` (v2/v3 add
one host-gate conjunct in `primitives.cpp`); the bf16 arm, the two-pass
f16/f32 partial formats, and the arithmetic order are untouched:

1. **v1** — K and V re-declared as `uint` word views; a lane's two
   adjacent f16 elements (host gate pins `k.strides()[3] == 1` and
   `v.strides()[3] == 1`, and `q_dim = 2 * lane` keeps lane bases even)
   load as one word, widened by `unpackHalf2x16` (widens exactly the
   bits `float(x)` widens). Plus software pipelining: each iteration
   pre-issues the next key's pairs before the online-softmax chain, with
   runtime bound guards and an odd-parity fallback in the pair loader.
   **Result:** monotonic regression growing with k_len — screen kernel
   time +1.5% / +6.8% / +9.2% at k=30/1024/1053; battery ctx1024
   −10.2%. Mechanism: Honeykrisp predicates the in-loop guard branches
   and the fallback stitch, executing both load paths every iteration.
2. **v2** — every branch removed from the hot loops. The host gate now
   refuses the f16 native route unless item offsets (byte offset `% 4`)
   and the kv-head/key strides of q, k, v are all even — then every
   element base is even and a pair is one unconditional word load (true
   for every decode cache: fresh `[2, keys, 64]` f16 arrays with
   multiples-of-64 strides; anything else keeps the f32 composition).
   The prefetch index clamps with `min` instead of branching.
   **Result:** battery flat (short −0.1%, ctx1024 +0.1%), dispatches
   still 201/token — but the screen stays +7.6% at k=1053 (blocks=128)
   while k=1024 (blocks=64) recovers to noise.
3. **v3** — prefetch dropped entirely; the word-view pair loads ride the
   exact base loop shape (same load positions, same arithmetic), so the
   A/B isolates load granularity alone. **Result:** battery pooled
   +1.2% ctx1024 / +0.02% short — noise; screens −1.8% to −4.1% at
   k=30/1024, mixed at k=1053.

## What the measurements say about term B

- The in-model marginal cost is ~0.045 us per key per dispatch (77.7 us
  dispatch gpu-time at k=1024 against ~34 us fixed), and the unique-byte
  stream is 539 KB per dispatch (2 kv heads x 1053 keys x 256 B, already
  deduplicated ~7x by L2 across the workgroups sharing a kv_head — the
  attribution's byte model only closes with that dedup). That yields
  **11.4 GB/s of unique bytes on jw16 — the attribution's 11.53 GB/s
  exactly**.
- v3 moves the identical bytes through half the load instructions in the
  identical loop order and the battery does not move: the ~11 GB/s rate
  is not load-granularity-bound and not in-thread-MLP-bound. It is the
  memory system's service rate for this access shape (32 lanes x 4 B
  inside one 128 B row, workgroup-synchronous key walks), which
  in-shader scheduling cannot change.
- Both pipelined arms regressed specifically in the blocks=128 regime
  (k>1024: four sequential logical blocks per subgroup, ~8-key walks,
  16 KB key stride) while blocks=64 (k=1024) was neutral for v2 — the
  blocks=128 regime is where Honeykrisp's scheduling differs from Metal.
  The in-model battery hides this at this model size because the
  attention delta sits inside ±8% leg noise.

**Next attack is outside the shader.** The evidence points at the
driver/memory-system layer: (a) a Honeykrisp-side trace of L2 sector
traffic for this dispatch (does the 7x kv-head dedup actually hit L2, or
does each repeat-head workgroup re-fetch from DRAM?); (b) a
workgroup-geometry change — one workgroup per kv_head computing all 7
repeat heads eliminates the dedup question entirely but multiplies the
per-key subgroup reduction by 7, and the exp/reduce chain is the
remaining serial op in the loop; (c) asking upstream Honeykrisp what
cache policy 16-bit SSBO loads take on AGX.
