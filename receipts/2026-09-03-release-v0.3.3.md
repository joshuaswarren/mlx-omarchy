## What went wrong, on the record

The first publish carried ONLY the x86_64 (cp311) wheel, built on the
dev box. Every prior stable release carried an aarch64 cp314 wheel as
well; this project's users are on Apple Silicon. The release notes
disclosed the gap, but disclosure is not delivery: for a few minutes
the Latest release could not serve the platform it exists for. The
asset gate passed the single-wheel release because it verified hashes,
version identity, build-commit stamps, and feature strings - and never
asked whether the release can run on the target platform. A gate that
approves an unusable artifact produces false confidence; that is the
same failure family the gate was built to close.

Fixes, all landed:

1. Notes amended within minutes, before anything else: the x86_64 asset
   was marked a development-platform build and the aarch64 wheel was
   announced as incoming.
2. The aarch64 cp314 wheel was built at the tag by BenchQueueM1 on the
   M1 (`jwm1`), scp'd to the dev box, hashed after transfer, verified
   locally, uploaded, and gate-verified.
3. `scripts/verify-release-assets.py` now FAILS a release whose wheels
   do not cover the required platforms (stable: linux_x86_64 AND
   linux_aarch64; `-diag`: linux_aarch64), and checks each wheel's
   filename platform against its `dist-info/WHEEL` Tag.
4. `docs/release.md` now names the required platforms, the wheel for
   each, and the machine each is built on.

compiled-tape gate on Apple GPUs, and the provenance/traceability work.

`docs/known-defects.md` at the tag. The measured numbers in the notes
come from an aarch64 build of the same source tree (`56cb642`) on the
M1, and the notes say so.
