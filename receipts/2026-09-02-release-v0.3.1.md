### aarch64 (jwm1, real Honeykrisp, no override flag) — 20/21 PASS, 1 FAIL

Fresh venv on jwm1, downloaded wheel, numpy added: `mlx version: 0.32.2.dev20260903`,
`device: Device(gpu, 0)` — the real Honeykrisp GPU. 20 checks PASS (the full v0.3.0 probe
set, all v0.3.1 fix classes including the trig gate eagerly and inside compiled tapes, GQA
SDPA exact at 5.5e-7, W11 deviation matching its disclosure at 3.41). **1 check FAILED**:

- `LogicalAnd 33 bools` — the check asserts the device-side `mx.all()` reduction over the
  33-element result. Root cause isolated, fresh process, deterministic: `mx.all` over a
  boolean array returns False for all-True input at EVERY size from 5 upward; sizes 1-4
  are correct; all-False input is correctly False. BoolAllFix's later hardware map widened
  this: `mx.any` is ALSO affected (a single True at index >= 4 is dropped, so mostly-False
  arrays reduce to False), axis reductions on a (2, n) shape fail from n = 3, and the
  per-position map at 33 shows positions 0-3 and 16-19 correct while every other position
  past the first word reads falsy - positional, with no clean size-based workaround. Cause
  pinned: `reduce_general.comp`'s `load_truthy` dynamic shift-then-mask byte extraction,
  the fifth confirmed site of the driver's dynamic byte-extraction miscompile family;
  `mx.logical_and` is green on the same buffers, isolating the defect to the reduction's
  load. The release-page warning was widened accordingly; the verified fix ships in
  v0.3.2.

Regression question answered: the published **v0.3.0** aarch64 wheel shows the same
defect (n=4 True, n=5 False, n=33 False in a fresh venv). This is pre-existing, NOT a
regression from `959c7a0`'s byte-extraction work, and predates it — a long-standing
coverage gap: the C++ battery, 828,139 assertions, never exercised a bool All-reduction
wider than one word on Apple hardware. The probe caught it because its LogicalAnd check
used a device-side `mx.all`, exactly the hardware-vs-rasterizer difference this release's
hold was about.

Disposition (Main): disclose, do not yank, fix forward to v0.3.2. The v0.3.1 release page
now carries a prominent warning at the top with the one-line reproduction and workarounds
(`bool(np.array(a).all())`, or an explicit CPU stream; the `astype(int32)` sum path refuses
by name). The defect ledger `docs/known-defects.md` carries the live entry with the
platform, sizes, and the coverage lesson.

### Why this hold-and-verify sequence mattered

The two verification signals point in opposite directions, and both are true. The
semaphore crash appeared 6 times in 50 runs on the dev box's software rasterizer and zero
times in 100 runs on the actual target hardware. The M1-only wrong values in scatter,
`LogicalAnd` and `select` were invisible on the dev box and only appeared on hardware.
Neither machine alone is sufficient, which is why this release was held for a hardware
run: that hold caught three release-candidate findings (all resolved to test-side causes:
a g++ 16.1.1 aarch64 `std::vector<bool>`-proxy miscompile of a test's host reference,
stale post-FCAS guard assertions, and a probe with a hardcoded `offset=0`), and the
published-artifact probe then caught the bool All defect on the real target.

## Build-flag caveat recorded for contributors (does not block the release)

`omarchy_distributed_tests` fails three assertions when hand-built with
`MLX_BUILD_CPU=OFF`: `is_available("ring")` is a build property, and ring.cpp only
compiles under the CPU backend. All project build scripts pin `MLX_BUILD_CPU=ON`, the
shipped configuration is green, and both M1 batteries confirm distributed 9/9. A
hand-rolled cmake line without the flag produces three bare CHECK failures that say
nothing about why.

## Verdict

**v0.3.1 is published as Latest with prerelease=false and both wheels attached; both
published wheels hash-match their verified builds.** The x86_64 leg is fully verified on
the published bytes. The aarch64 leg verified 20/21 on the real target and surfaced one
pre-existing, deterministic, silent wrong-value defect - boolean reductions (`mx.all` and
`mx.any`) misreduce positionally past the first 32-bit word, whole-array and axis alike,
cause pinned to `reduce_general.comp`'s `load_truthy` dynamic byte extraction (fifth
confirmed site of the family) - disclosed prominently on the release page and ledgered
for the v0.3.2 fix. The release
still strictly dominates v0.3.0, which ships a 6/50 crash rate plus wrong values on the
same hardware.
