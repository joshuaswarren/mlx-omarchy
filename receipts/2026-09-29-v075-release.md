## Correction

The first version of this receipt claimed a multi-hour "logged-out GitHub
outage" blocked the installed-from-release gates, and blamed GitHub. That was
wrong. The gate harness scripts and probes on the release seat spelled the
repository owner `joshuawarren` (a different, existing user) instead of
`joshuaswarren`; every 404 observed from 13:05–14:23 UTC was that typo, and
the correct-owner URLs answered 200 throughout. The git-bundle workaround in
the earlier build-provenance text was likewise unnecessary — plain anonymous
clones over HTTPS work. No GitHub-side fault occurred; `www.githubstatus.com`
reported all systems operational throughout, which was accurate.

## What shipped

The one-line installer fetches `serve/mlx_omarchy_assistant/*` from the latest
release tag; v0.7.4 predates that package, so a fresh install aborted at that
step. From this tag the installer ships the assistant, the serve CLI, and the
wheel from the same commit, plus the elementwise-add fix
(`omp_binary_op_type`, `overlay/mlx/backend/omarchy/primitives.cpp`) and the
Qwen3-TTS codec-decoder speech fix with its focused regression
(`tests/test_qwen3_tts_codec_regress.py`).

## Re-cut 1 (gate-caught installer defect, 2026-09-29)

The first installed-from-release gate run caught a fresh-install breaker
before promotion: the tag's `install.sh` fetched a literal list of four
mlx-lm patch files while `scripts/apply-mlx-lm-patches.sh` applies seven, so
a clean install aborted with `error: patch file missing:
patches/mlx-lm-qwen35-qk-scaled.patch` (exit 5). Fixed in `e45c08a7d`: the
installer now reads the patch names from the apply script, with
`tests/test_serve_bootstrap.py::PatchFetchTests` failing on the old installer
and passing on the fix. The tag was moved to the fix commit and both wheels
were re-stamped. Same gate class as the v0.7.4 one-line fix.

### Harness script fixes (not product changes)

- Gate 3 first failed with `laya-mlx: no usable converted artifact and no raw
  snapshot to convert (offline mode)`. Two causes: (a) a fresh assistant home
  has no converted Laya artifact, and converting from the shared HF cache
  failed because the cache holds only a partial raw snapshot for the pinned
  revision — the conversion-from-cache path is a real product gap, recorded
  here as an observation; (b) the first rerun copied the artifact under the
  wrong home path. The passing configuration uses the host's prepared pair
  home (locked Everyday pair with the converted, hash-bound Laya artifact),
  read-only from the gate's point of view. No pass condition changed.
- Gate 4 first ran as a skip-pass (both tests honest-skipped: no
  `MLX_OMARCHY_TTS_TEST_PACK`, and the test imports `mlx_omarchy_assistant`,
  which the installer places under the install prefix rather than
  site-packages). Fixed by exporting `MLX_OMARCHY_TTS_TEST_PACK` to the local
  voice pack, installing the installer's own `--voice` dependency set
  (`mlx-audio==0.5.6 --no-deps` plus its floors) into the installed venv, and
  prepending the install prefix to `PYTHONPATH`. After the fix both tests
  executed (`Ran 2 tests ... ok`).

## Driver requirement on Apple Silicon (Omarchy)

This wheel requires the Honeykrisp fork driver (`joshuaswarren/mesa-1`,
branch `honeykrisp-omarchy`) as the active Vulkan ICD. See
[docs/install-omarchy.md](https://github.com/joshuaswarren/mlx-omarchy/blob/main/docs/install-omarchy.md). Wheels ship kernels, not the driver.
