## What shipped

Two data-correctness defects found by the T6021 jw14m2 macOS capture
(oracle: ane-linux-experiments
`receipts/2026-09-17-jw14m2-t6021-macos-capture/`, commit `6da245f`):

1. **macOS phandle byte-swap.** `AAPL,phandle` was read big-endian;
   ioreg OSData presents cells in HOST byte order (little-endian on
   arm64). v0.6.4 shipped `0x69010000` where the true phandle is `0x169`.
   5 published macOS rows carry 24 swapped values; each is exactly
   recoverable by a 32-bit byteswap. Fixed to read little-endian; the
   Linux procfs DT path was already correct (spec big-endian) and is
   untouched.
2. **pmgr reg capped at 64 bytes.** t6021 reality: 1168 bytes / 73
   ranges; t6002: 3856 bytes / 241 ranges. Cap raised to 4096 bytes /
   256 ranges with decoded ranges (u64-LE, u32-LE for the 4/8-byte
   stragglers such as mapper reg `<00000000>`), `reg_ranges_total`, and
   explicit `truncated[]` markers. Honest accounting, never silent.

macOS capture upgrade (the T6021 findings, now automatic, all bounded):

- ANE/DART/mapper reg decoded into ALL ranges in the Linux
  `0xADDR/0xSIZE` form for field-to-field cross-OS diffing; ane ranges
  classified `ane_mmio` / `pmgr_block` / `pmgr_plus_c000`.
- `set_base_candidate` = pmgr block base + `0xc000` plus
  `driver_window_confirms` (Apple's own ane device granted exactly that
  window: True on t6021, False on t6002 — a candidate, never a derived
  fact; Linux/m1n1 enumerates the cluster itself).
- Driver identity: `H11ANEIn` matched, bundle id, kext version 9.512.0,
  arch `h14g` (t6021) / `h13g` (t6002), cores, ANEVersion.minor (128.17
  / 96.17), instance count, and `classes_empty` — the explicit negative
  result for `AppleH13ANEInterface` / `AppleH16ANEInterface` (recorded
  via the real zero-match ioreg shape: exit 0, zero bytes of output).
- Platform identity decoded: `target-type` (`J414c` / `J375d`),
  compatible list, `platform-name` hex decoded to the ASCII SoC id
  (`t6021`, `t6002`) — no more hand-decoding hex blobs.
- ANE compiler provenance: framework 9.509.0, kext 9.512.0, daemons
  `/usr/libexec/aned` + `/usr/libexec/aneuserd`,
  `ANECompilerService.framework` absence, binaries-cache-resident as a
  known condition (plutil/test probes, not failures).
- `dart-id` (0x25 on t6021); `#iommu-cells` recorded as an explicit
  unavailable-on-macOS miss (per-node null + one `truncated[]` marker).
- `IOInterruptControllers` / `IOInterruptSpecifiers` no longer
  repr-mangled by 1-element list wrapping (v0.6.4 shipped
  `"[b't\\x03\\x00\\x00']"` as a string).

## PROCESS DEFECT, named: the release was published before Gate 2 completed

`gh release create` publishes by default and I used it without
`--draft`, so v0.6.5 was user-visible while the ctx1024/short decode
legs were still running — publishing on unresolved gate status. Both
legs subsequently passed (table above), so no unpublish was needed, but
the exposure was real and this is the same failure mode as v0.6.3's
first attempt. **Standing rule adopted for future releases: create the
release as a DRAFT, run every gate against the uploaded bytes, publish
only after all are green. The draft costs nothing; an unpublish is a
user-visible event.**

## Read-side correction for the affected published rows (approved)

The 5 rows carrying swapped phandles are immutable (no delete route).
Owner-approved repair shape: a **deterministic, provenance-gated
read-side correction** in `scripts/query_community_data.py`:

- The affected rows carry no collector-version field (`mlx_version` is
  the MLX build, `source_commit` null), so they are pinned by an
  explicit 5-entry content-sha256 allow-list — no value-magnitude
  heuristic, which would silently corrupt a legitimately large phandle.
- When `show` serves one of those rows, `macos.*_nodes[*].phandle` is
  byte-reversed in the served view (0x69010000 -> 0x169) and the
  correction is emitted twice: a `_read_side_correction` key in the
  JSON and a stderr note.
- No stored data is mutated; the raw rows remain on the wire for
  consumers who want them.

Live-verified 2026-09-17: `show a3e974f8…` serves corrected phandles
`0x169/0x16a/0x16b` + note; unaffected rows are untouched.
