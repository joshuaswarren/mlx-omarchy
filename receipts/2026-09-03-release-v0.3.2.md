## Version scheme change (process finding, caught before the tag)

v0.3.1 and v0.3.2 were built the same day under upstream's date-only dev segment
(`setup.py` builds `dev{YYYY}{MM}{DD}` from the pinned tarball), producing the SAME version
string and the SAME wheel filename. Consequence: `pip install --upgrade` from v0.3.1 to
v0.3.2 would be a silent no-op - the correctness fix would not reach the users who had
already upgraded once. Caught by Release031 flagging a filename coincidence, not by any
test. Fix: `patches/mlx-version-time.patch` changes the dev segment to
`dev{YYYY}{MM}{DD}{HH}{MM}` - one PEP 440 integer, monotonically increasing, generated
against the pristine pinned tarball and applied by `prepare-mlx.sh` after the other five
patches. Main verified end to end on a fresh worktree that the patch applies and that pip
orders `202609030507` above `20260903`, so `--upgrade` actually upgrades. v0.3.1's
published artifacts were not touched. The v0.3.1 release page and the v0.3.2 release notes
carry force-upgrade instructions for anyone holding the identically-versioned v0.3.1.

## Verification lineage (why the probe exists)

v0.3.1's published-wheel probe caught the boolean-reduction defect that 828,139 in-tree
assertions never reached; this release's probe is that probe, permanent and widened to the
full matrix, committed so the next release inherits it instead of reinventing it. The fix
itself was device-probed rather than trusted by analogy - `select.comp` had proven the
byte-extraction macro is context-sensitive on this driver.

## Scope note

v0.3.2 is deliberately narrow: the boolean-reduction fix and its documentation. Two
staged performance slices (submission-ring + descriptor cache, compiled-tape fusion) are
held pending hardware verification and are NOT in this release.
