## 2. Changes (3 commits, overlay-python only, libmlx untouched)

- `3f08e59b0` fuse preemphasis into the windowing kernel and magnitude into
  power: 8 → 6 runtime pipelines. Per-element arithmetic order unchanged.
  The standalone preemph kernel stays as an evidence-only dispatch for
  capture-stages qualification (the pinned macOS stage set includes
  preemph); the capture dispatch gate moves 8 → 7.
- `91b1e4224` restore the `_preemphasize` wrapper the fusion commit dropped.
- `56d71401e` sparse mel dot: the pinned 128×257 filterbank has ≤12
  nonzeros per row (mean 3.9); the kernel walks 12 packed nonzero bin
  indices per row in the original visit order, reconstructing each term's
  accumulator slot from its block/relative/lane position. Padding rows use
  zero-weight bins — the emulated fma32 contract returns the accumulator
  unchanged for a zero first operand, so padding/skipping is bit-identical
  to the dense accumulation. Verified off-device with the certified
  `dotpr._fma32/_add32`: dense vs sparse projections bit-identical at
  normal, subnormal (2^-130 scale) and large scales.

Rejected: native-precise arithmetic. `test_native_fma_does_not_meet_the_
exact_custom_kernel_contract` pins native fma one ulp off (0x4748616A vs
correctly-rounded 0x4748616B). Note: on today's driver (7faf04c) that test
now FAILS in the opposite direction — native fma returns the correctly
rounded 0x4748616B — i.e. the driver's native fma behavior changed since
the contract was pinned. Re-certification of native arithmetic is a
contract decision for Main/mesa lane, not this lane.
