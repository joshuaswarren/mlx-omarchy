## Findings: the SET-base derivation path, and what a submission can and cannot supply

The driver's per-SoC ANE constant is the pmgr SET-block base (upstream
m1n1 `ps_map`, M1-family only: ane `0x23b70c000`, ane0 `0x28e08c000`,
ane1 `0x28e684000`, ane2 `0x228e08c000`, ane3 `0x228e684000`). Live
captures this session (jwm1 T8103, jw16 T6001) confirm how it derives:

- The SET region announces itself inside the ANE pmgr block as the
  ane_* pwrstate cluster at/above 0xc000: t8103 has `ane_sys@c000
  power-controller@470 ane_sys`, then `ane_sys_cpu@c000`,
  `ane_base@c008`, `ane_set1..5@c010-c030`; t6001 has `ane_sys@268`,
  `ane_sys_cpu@2c8` (a power-domain BELOW 0xc000 — not part of the
  cluster), then `ane_set0@c000`, `ane_base@c008`, `ane_set1..5`.
- On both known-good SoCs the cluster start is exactly **+0xc000** from
  the pmgr block base, and `base + 0xc000` equals the m1n1 ps_map
  constant (0x23b700000→0x23b70c000, 0x28e080000→0x28e08c000). The
  regression test (`test_set_base_derivable_from_pmgr_topology`)
  derives exactly this from the captured fixtures, and both live
  submissions reproduce it.
- The SET region is NOT a declared register: every child is a plain
  `apple,<soc>-pmgr-pwrstate` node — the offset must be derived, never
  read from a DT "set" reg. Reads of the SET block are safe (the driver
  maps it read-only; only writes external-abort), so a derived base is
  verified by reading, not guessed into a write.
- Upstream ps_map's ane1/ane3 (`0x28e684000`/`0x228e684000`) sit at
  +0x4000 of the second block `power-management@28e680000` — different
  offset, same block+cluster derivation, which is why the capture ships
  ALL `apple,pmgr` blocks (cap 8) rather than the first.
- t6020 wrinkle (community row `3da10060…`): t602x exposes ane domains
  at 260/2e0/4000/4008 and NO cluster at 0xc000. For such trees the
  +0xc000 value carried by the t8103/t6001 references is the
  hypothesis to read-verify, not a derivation — the capture says which
  case applies (`children` at/above 0xc000 or their absence).

**A submission CAN supply:** the pmgr block base(s) and the complete
pwrstate offset topology (hence the SET-base candidate on M1-family
shapes), the ane node's MMIO reg or its documented absence, DART reg
ranges/#iommu-cells for the ANE IOMMUs, boot-chain firmware identity,
root compatible/model, and the booted DTB identity (when /sys/firmware/
fdt is readable).

**A submission CANNOT supply (and why):** the SET base on trees with no
exposed ane cluster at/above 0xc000 (t602x: only the two-reference
+0xc000 hypothesis applies, to be read-verified); the DTB hash on
kernels where `/sys/firmware/fdt` is root-only 0400 (jwm1 and jw16
both recorded `dtb_sha256: null` for a non-root run — a sudo run
captures it); the pwrstate offsets from macOS (IORegistry exposes the
pmgr BLOCK base, e.g. `8E080000` on Mac13,2, but not the children —
macOS rows cross-check a base, Linux rows or m1n1 on the target machine
remain the authoritative route for the offset).
